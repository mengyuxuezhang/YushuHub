# 600 路模型并发隔离压测与优化方案

日期：2026-11-12。管理端基线：YushuHub `78df029` / `1.9.70`。

本文保留优化前的观测；优化后的实现与复测见 [优化验收报告](MODEL_CAPACITY_OPTIMIZATION_2026-11-12.md)。脚本随后已用于新代码复测，复现旧结果须使用本文基线代码与同样的测试夹具。

## 结论与适用范围

真实管理端能够在本次隔离环境中保持 600 路文本 SSE 生成，并完成响应与积分结算，但存在明显的突发延迟、会员补建死锁和慢客户端缓冲风险。不能据此承诺现网服务器能稳定承受同等负载。

本轮只新增本地压测脚本、观测代码和本报告；未修改产品业务逻辑，未部署、重启或访问线上业务服务，也没有调用付费供应商。

## 环境与方法

- 本机 Windows，Intel Xeon D-1581 1.80GHz，32 逻辑核、约 64GiB 内存；Node.js v24.14.0。
- 真实管理端独立子进程，监听 127.0.0.1 随机端口，V8 old-space 上限 768MiB。该参数不是整个进程的 RSS 上限，应用未限制 CPU。
- 新建 MySQL 8.4 Docker 容器，绑定本机随机端口，限制 2 CPU / 1GiB；生产默认连接池 10，另做 30 连接的实验性参数对照。
- 600 个虚构用户、独立会话、足额测试积分、一个共享加密模型 Key；普通场景预先建立有效会员记录。
- 流程经过真实 HTTP、鉴权、会员/模型权限、模型及价格查询、Key 解密、流式转发和事务积分扣减。未用假函数替换这些业务处理。
- 模型上游为本机模拟服务，返回有效 SSE、唯一请求 ID、usage 与 `[DONE]`；每次成功请求计费 1 积分。
- 观测预加载器拦截非 loopback HTTP/fetch，限制应用数据库只能访问本机 `capacity_*` 测试库。子进程仅接收明确列出的测试环境变量。
- 使用 legacy 官方权限捷径启动隔离实例，未覆盖真实授权中心、固定模式响应来源证明、New API 限流和付费供应商耗时。
- 本轮没有 Nginx、TLS 和公网链路；压测驱动和模拟上游同进程，应用另进程，MySQL 在 Docker 内。Windows 的计时、TCP 接纳和跨 Docker 数据库延迟均影响结果。

压测判断成功必须同时满足 HTTP 200 与收到完整 `[DONE]`；不能只看状态码。上游活跃请求峰值用于确认真正达到 600 路重叠，而不只是累计发起 600 次。

## 结果

### 正常会员、默认连接池 10

| 场景 | 成功 / 发起 | 上游活跃峰值 | 首字节 P95 | 应用 RSS 阶段峰值 | 积分消费流水 |
| --- | --- | --- | --- | --- | --- |
| 100 路瞬时，模拟生成 15 秒 | 100 / 100 | 100 | 1.37 秒 | 144 MiB | 100 条 / 100 积分 |
| 300 路瞬时，模拟生成 15 秒 | 300 / 300 | 300 | 3.05 秒 | 217 MiB | 300 条 / 300 积分 |
| 600 路瞬时，模拟生成 15 秒 | 528 / 600 | 528 | 5.22 秒 | 235 MiB | 528 条 / 528 积分 |
| 600 路持续，模拟生成 60 秒 | 600 / 600 | 600 | 5.70 秒 | 249 MiB | 600 条 / 600 积分 |
| 600 路，单请求输入约 256KiB | 379 / 600 | 379 | 5.84 秒 | 478 MiB | 379 条 / 379 积分 |
| 600 路慢读，每请求约 512KiB 输出 | 600 / 600 | 600 | 21.16 秒 | 501 MiB | 600 条 / 600 积分 |
| 600 路同一用户请求 | 600 / 600 | 600 | 6.01 秒 | 502 MiB | 600 条 / 600 积分 |

说明：慢读用例故意暂停客户端读取 15 秒，首字节指标因此包含人为暂停，不表示服务端直到 21 秒才产生响应。阶段顺序运行，RSS 包含前序分配及 GC 保留，不应将阶段差值全部归因于当前场景。首字节对失败建连使用 0 占位，因此有连接失败的两行只用于描述整批观测，不作为成功请求延迟的独立分布。

600 路瞬时和大输入用例的失败是本机 TCP `ECONNREFUSED`，没有进入模型调用；应用保持运行。原因可能涉及瞬时连接的监听接纳/队列限制，尚未通过系统级 TCP 追踪证明具体参数。不能把此结果直接归因为 Linux 线上 Nginx 容量不足，也不能在报告中删掉这些失败。

### 控制建连速率的高频流式复测

每 100ms 发起 50 路，约 1.1 秒内发完；模拟上游每请求发送 600 帧、每帧 256 字符，目标持续 30 秒。与前面每秒约 4 帧的基础场景相比，这组增加了流处理负载。

默认 10 连接池：600 / 600 成功，上游峰值 600；首字节 P95 **8.12 秒**，响应完成 P95 **39.99 秒**；RSS 峰值 **254MiB**。驱动事件循环 P99 39.6ms，应用事件循环 P99 42.5ms；应用窗口 CPU 时间折算约 1.08 个逻辑核，包含 Node 原生工作线程。

结算核对：600 个不同请求 ID、600 条消费流水、合计扣除 600 积分；用户余额合计从 6,000,000 变为 5,999,400。本次没有发现重复扣费或漏记消费流水。

这组控制建连速率后全部成功，说明瞬时建连失败与持续 600 路生成需要分开评估。它不能单独证明是某个 backlog 参数造成前述失败。

实验性 30 连接池在相同虚构业务配置和高频输出参数下：600 / 600 成功，上游峰值 600；首字节 P95 **11.31 秒**，完成 P95 **53.87 秒**；RSS 峰值 **279MiB**，连接等待队列峰值 571，应用事件循环 P99 75.4ms。600 条唯一消费流水、600 积分及最终余额核对一致，Key 成功计数增加 600。

该次扩池没有得到性能改善，不能推荐“直接加到 30”作为解决方案。两组为先后单轮探索对照，并非多轮随机交叉实验；驱动事件循环 P99 也从 39.6ms 变为 64.4ms，模拟器实际发帧会随负载变慢，因此不能把全部差值因果归于连接池大小，更不能视作真实供应商生成速度。应在消除热点、削减 SQL 后做多轮 10/20/30 对照，再选生产参数。

### 缺少有效会员记录的异常场景

先期故意未建立会员记录，从而触发免费会员补建。结果如下：

| 场景 | 成功 | 失败 |
| --- | --- | --- |
| 100 路首次补建 | 10 | 90 |
| 后续 300 路（部分用户已补建） | 54 | 246 |
| 后续 600 路（部分用户已补建） | 150 | 450 |

失败接口返回 HTTP 400 与 `Deadlock found when trying to get lock; try restarting transaction`。它发生在上游请求前，不是供应商限流。后续各组用户状态受前组补建影响，不应拿三行直接计算并发扩展曲线。

MySQL `SHOW ENGINE INNODB STATUS` 给出了锁循环：事务 A 持有 `ai_end_user_memberships` 用户/状态索引间隙锁，等待 `ai_membership_cards` 的 `free` 主键行 X 锁；事务 B 持有该会员卡行 X 锁，插入用户会员记录时等待 A 的间隙锁。InnoDB 回滚其中一方。

这证明会员补建路径存在真实并发问题，但不代表所有正常注册用户都有此问题：正常注册通常已配置会员。会员缺失、过期后的补建等场景需要专项覆盖。

## 瓶颈与优先级

### P0：会员补建事务及错误处理

涉及 `src/services/memberships.mjs` 的 `ensureFreeMembershipFallback`，由模型请求权限检查触发。

建议以用户主键锁作为同一用户的串行点，统一相关写入路径的锁顺序；避免“无会员记录的范围锁 + 共享会员卡 X 锁”交叉。共享卡配置应在必要时初始化，不能每次补建都无条件改写。事务保持短小；针对确定的死锁做有限次数、带抖动的事务级重试，确保权益赠送与流水仍然幂等。

数据库死锁是服务端暂时性失败，应映射为受控可重试的错误，不能原样暴露 SQL 错误并按客户端输入错误返回。不能通过全局降低事务隔离级别或删除余额锁来掩盖问题。

验收：600 个无会员用户并发首次调用，600 个同用户并发补建、会员过期、会员存在等组合均无重复权益，无未处理死锁；必要重试结束后有清晰错误与日志。

### P1：减少请求准备阶段的数据库工作与共享 Key 热点

600 路持续测试连接等待队列峰值 590；SQL 调用耗时含连接排队，不能把这些时间全部当作数据库执行耗时。代码与采样显示同一请求多次读取用户/会话，模型、权限、价格也逐请求查询；`last_used_at` 和 `success_count` 集中更新同一个 Key 行。

先复用请求内鉴权和用户上下文，精确按目标模型查询，减少不必要的全目录读取。模型和价格元数据可按组织、配置版本做有上限、可失效的缓存；余额、停用状态和权限撤销不得用长 TTL 缓存代替实时校验。Key 调度和统计需要独立设计：保留正确的选择与轮换语义，对纯统计字段考虑批量汇总，不得改成不可恢复的“丢了也不管”。

连接池参数应可配置，并配合数据库容量选择；不能把 10 连接理解成最多 10 路模型请求，也不能直接扩成 600 连接。数据库连接只应覆盖短查询/结算事务，不应在等待生成期间一直占用。

验收：同样 600 路复测，记录进入上游前的排队时间、SQL 数量与数据库实际执行时间；首字节延迟显著下降，计费与权限行为保持。

### P1：流式背压、超时与慢客户端保护

慢读用例观测到约 10,200 次 `res.write()` 返回 false，单响应可写缓冲峰值约 289KiB；当前代码仍继续读上游。它证明缺少背压处理的分支已实际触发，不只是一条静态建议。

转发应在写入返回 false 后等待 drain，同时监听关闭/错误并解除监听；客户端断开立即取消上游并释放资源。增加可配置的流空闲和最长执行时间，区别于现有的上游响应头超时，避免永久不结束的请求长期占用资源。不能用过短固定超时误杀合理长推理。

验收：慢读、断线、永不结束上游、断线与结算交错场景下缓冲有界，活动请求数回落，无监听器泄漏，扣费策略符合已确定合同。

### P1：入口并发、请求内存预算与上游配额

设置全实例、每用户及每供应商的并发预算，并提供有界队列、最大排队时间和明确的 429/503 响应。上限须由复测数据决定，不将本次 600 成功直接当生产默认值。

现有单请求 JSON 上限 20MB；600 路接近上限的输入仅原始体积就约 12GB，本轮出于资源控制没有尝试该规模。应按请求大小设置总在途字节预算和输入限额，考虑无 Content-Length 请求，保护合法长上下文，而非仅限制请求条数。

### P2：部署链路和规模化验收

在后续独立 Linux 环境加入与生产相同的 Nginx/TLS、CPU/内存限制，检查实际生效的文件句柄、连接接纳队列、worker_connections、SSE buffering 和超时。模拟上游限流、慢响应和重试，限制重试放大。

高频流式场景已消耗约一个逻辑核的 CPU 时间，后续还需分离测量事件循环、JSON 处理、日志及原生线程开销。多进程前先审查本地文件状态、授权缓存、调度器和全局配额是否支持并行，不能直接打开 cluster 并假定线性扩容。

优化后的验收顺序：相同参数 A/B → 600 路持续至少 30 分钟 → 突发、慢读、断线和大上下文 → 余额/流水、Key 状态及内存恢复 → 最后经明确授权进行生产灰度。

## 复现、证据与清理

脚本：`scripts/capacity-600.mjs`、`scripts/capacity-preload.mjs`；锁证据采集器为 `scripts/capacity-capture.mjs`。依赖本机 Node、Docker、预先存在的 `mysql:8.4` 镜像和已安装的项目依赖。不读取真实环境配置或复用已有数据库。

PowerShell 普通完整场景：

```powershell
$env:CAPACITY_REPORT='results-warm.json'
node scripts/capacity-600.mjs
```

高频流复测：

```powershell
$env:CAPACITY_REPORT='results-ramp10.json'
$env:CAPACITY_CASE='600-burst'
$env:CAPACITY_RAMP='1'
$env:CAPACITY_TEXT_RATE='1'
node scripts/capacity-600.mjs
```

设置 `CAPACITY_POOL_SIZE=30` 只改变隔离进程的观测预加载器创建连接池的参数；不修改正式产品代码。`CAPACITY_COLD=1` 可重现缺会员场景，`CAPACITY_QUICK=1` 可运行单请求冒烟。切换测试时应清除不适用的环境变量。

本地证据保存在 `capacity-results/`，该目录已加入忽略清单，包含原始结果 JSON、测试日志与隔离密钥文件，不应整体提交。初轮 SQL 观测窗口在消费流水齐全后结束，部分 Key 统计收尾可能跨阶段，因此不能将其计数当作精确的每请求 SQL 数量；最终参数对照脚本会额外等待 Key 成功计数落地。

脚本 finally 停止本次创建的应用、模拟上游及唯一命名数据库容器。停止后的测试数据库保留以供复核；仅允许按本次 `yushu-capacity-*` 的确切容器名清理，不能批量停止或删除其他容器。
