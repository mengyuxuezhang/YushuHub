# 授权中心的源码、部署与信任边界

2026-11-02核对。适用于`feat/license-center-direct-newapi`，不是正式发布说明。

## 当前实际结构

授权中心是独立服务，尚不是独立仓库。源码与管理端同在YushuHub开发分支：

| 部分 | 源码入口 | 部署与数据 |
| --- | --- | --- |
| 官方授权中心 | `cloud/license-center/server.mjs`、`web-admin/src/license-center`、`src/services/authorization/center.mjs`及运营模块 | 官方独立进程和MySQL库，保存签发资料、运营账号和审计 |
| 代理经营管理端 | `cloud/ai-admin/server.mjs`、`web-admin/src`，授权客户端为`src/services/authorization/runtime.mjs`及`deployment-client.mjs` | 代理自己的服务器、经营库和部署凭据 |
| 官方构建/保护资源/更新 | `src/services/authorization/official-services.mjs`等 | 官方服务器向其自行配置的可信授权中心核验，不接受代理自行声明的权限 |

普通管理端启动入口不注册中心运营路由。知道中心源码、另起一套中心，均不等于拿到官方中心数据库、运营账号或签名私钥。正式私钥和运行凭据必须保留在官方受控环境，不随仓库或下游部署交付。

## 完整源码交付的实际限制

代理控制完整源码与服务器时，可以改写本地许可判断、信任的中心地址或公钥、服务商限制等，使其本地程序绕过官方版本的软件限制。是否同仓库不是根本原因；即使完全不交付中心源码，也不能承诺其无法修改本地管理端。

这不等于取得官方授权。他们自行签发的凭证不会通过官方中心核验；不能据此调用受官方授权保护的构建、更新和保护资源，也不能增加现有New API账号余额。官方服务必须使用自己控制的中心配置并关闭生产旧授权兼容通道；不能信任下游传入的中心地址、权限标志或自签凭证。代理改用自己的构建或供应商，则属于本地源码可修改的边界，不能描述为“绝对禁止”。

## 当前交付边界与后续建议

`scripts/pack-zip.ps1`目前按目录排除后复制运行代码，没有专门剔除`cloud/license-center`、中心运营模块及`web/license-center`。因此现阶段不能声称下游交付包已经只包含授权客户端。当前分支尚未正式发布，正式交付前须核对并收窄交付清单。

建议后续将官方授权中心迁入独立私有仓库，并拆分中心发布包与代理管理端发布包；代理侧只保留接入协议、验签公钥、部署客户端和必要的公共类型。这能隔离官方运营源码与交付职责，但仍不能防止完整源码持有者改写本地校验。此处为建议与待办，尚未实施拆仓或交付包拆分，不应据此新建重复项目或宣称已经完成。

已经推送到公开仓库的历史代码不会因为后续迁私有仓库而自动变为秘密；不以隐藏历史源码作为安全保证。签名私钥、账号凭据和官方侧的独立校验才是官方授权的信任边界。

如果业务目标是让每次本地模型调用都无法脱离官方控制，需要把必要执行环节保留在官方托管侧，或减少源码交付范围；这会改变已确认的源码部署与直连New API方案，不能在本次文档说明中静默引入新的网关。
