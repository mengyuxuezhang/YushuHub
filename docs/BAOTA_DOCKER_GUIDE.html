本文固定首迁基线为管理后台 1.9.68。普通更新仍为 1.9.68；内部 Docker 候选不是首迁前置版本。未收到维护者发行单、生产公钥指纹和窗口批准，请只阅读，不执行变更命令。

先看这一页

确认已运行 1.9.68→ 备份与核对→ 1.9.68 同版首迁→ 检查原域名→ 后续批准升级

这不是把经营后台清空重装。迁移工具保留同一数据库和持久目录，绑定原端口与授权身份；首次迁移后仍显示 1.9.68 是预期结果。

谁来操作负责什么
代理商确认域名、后台版本和备份，检查登录、授权状态、项目及经营记录；在宝塔查看容器状态和日志。

当前不能只靠面板点“创建网站”完成受管迁移。没有宝塔终端或受控 root 维护权限时，请交给维护者，不要另建同名容器或导入通用 Compose 模板。

1 · 认清宝塔入口

宝塔的“网站”和“容器”是不同列表。“Docker→网站”没有记录，不能据此判断 Docker 没装、容器没运行，或必须重建后台。

入口本手册怎么使用
左侧“网站”保留原管理后台域名、证书和实际生效的反向代理站点。
Docker→容器按维护者提供的容器名查状态、镜像和日志。官方说明，终端创建的容器也能在此查看。[1]
Docker→网站 / 运行环境这是宝塔的建站入口，不是已运行容器的完整清单。不要在此再安装一个同域名的后台。
Docker→容器编排宝塔提供 Compose 管理入口。[1] 本工具生成的是受保护的 compose.json，不同面板版本是否自动列出尚未实测。看不到编排时，先查“容器”和终端；不要复制成第二个项目。
左侧“终端”维护者执行本文标出的命令。必须是后台所在这台服务器，不是另一节点或本地 Windows 终端。

保留原宿主 Nginx 是本手册主路径。“Docker→网站”的 Nginx 按钮和普通“网站”的配置入口不能视为同一个配置位置；也不能仅凭该按钮判断 Nginx 的实际进程或网络。维护者要确认哪一个服务正在接收原域名的 80/443 请求。

若反代实际运行在 bridge 网络的 Nginx 容器内，它的 127.0.0.1 是那个容器自身，不是宿主。当前后台绑定宿主回环地址，这种前置架构需单独核定；不要为绕过它把后台或数据库改成公网监听。

界面参考：官方 Docker 网站教程注明 9.3.0 以上版本；较新版菜单可能调整。[2][3] 截图中的 Nginx 版本不是宝塔版本。本文未在某个宝塔版本实装点选，不能标成“宝塔 13.x 已实测”。

2 · 环境检查：全部通过才继续

检查项通过条件 / 不满足时
现有后台磁盘版本、本机运行 API 和原域名 API 都是发行单指定的 1.9.68。其他版本先按既有升级流程到基线，再重新检查。
系统Linux amd64 / x86_64，原生 systemd，Python 3.8+、OpenSSL 1.1.1 或 3、ss 与兼容现有数据库的 mysqldump。
宝塔已有 Docker复用本机 Engine；docker compose 插件 ≥2.30。只装有旧 docker-compose 不等于通过。已有 Engine 时不运行重装脚本、不重启共享 Docker 服务来试错。
原进程当前范围是 root 管理、一个在线 fork PM2 进程。宝塔项目若以 www 或其他用户运行，暂停交维护者评估；不要擅自提权或另启 root 副本。
数据库沿用同机、经维护者确认业务独占的库。保留现有本地 TCP 地址、端口、账户；不新建 MySQL 容器，不开放数据库公网访问。
域名与身份原 HTTPS 域名、授权模式、实例及公钥/密钥保持。center 不能为了迁移改成 legacy，也不重新激活或重建用户。
端口与守护保留此后台原端口；不能与其他站冲突。维护者核对并处理“此后台”的面板自动拉起、旧守护和计划任务，防止首迁后旧 PM2 复活。不要停其他站的守护或数据库。
路径与权限数据目录在该实例已审路径内，无未审外部目录/符号链接。容器使用 UID/GID 1000，迁移工具会处理本实例持久目录的所有权；须核对宿主 UID1000 是否与其他用户冲突，不做全盘 chmod/chown。
资源有足够磁盘存放镜像、数据库备份和持久文件备份。默认业务上限 256MiB、宿主预留 128MiB 是准入预算，不是最低整机配置或不会 OOM 的保证。
维护者：只读检查命令（不含密码）
id -u
uname -m
python3 --version
openssl version
docker info --format '{{.OSType}}'
docker compose version --short
command -v ss
command -v mysqldump
pm2 list

预期：root 的 UID 为 0、架构 x86_64、本机 Docker 为 linux，Compose 版本满足要求。宝塔的 mysqldump 可能在 /www/server/mysql/bin/mysqldump，由维护者核定；命令未找到不代表需要重装数据库。

以下示例统一使用占位站点和目录。先由维护者填好 APP_ROOT、APP_PORT；不要直接把示例替换成截图里的服务器地址。

APP_ROOT='/www/wwwroot/example-admin'
APP_PORT='7077'
# 先核对磁盘包版本（不是运行版本）
node -p 'require(process.argv[1]).version' "$APP_ROOT/package.json"
# 本机实际运行版本
curl -fsS "http://127.0.0.1:$APP_PORT/api/runtime-info" \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["data"]["version"])'
# 原域名实际运行版本；改为自己的原域名
curl -fsS 'https://admin.example.invalid/api/runtime-info' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["data"]["version"])'

预期：迁移前这三处均为 1.9.68，页面可以登录，原授权和原项目可用。若本机与域名不同，先排查反代目标/缓存，不执行迁移。

3 · 迁移前备份

先约定短维护窗口，暂停本后台的业务写入并记录维护方式。宝塔“数据库→备份”和站点备份可以作为入口，但只备份网页源码不够。

必须保留核对方式
原数据库一致性备份确认是正确业务库、文件非空、可在隔离环境读取；不把数据库密码写进命令参数或群聊。
原 .env、data、上传/发布及其他已审持久目录加密密钥文件与库中的密文必须配套。记录路径、权限和安全摘要，不展示内容。
原代码、依赖与 PM2 恢复定义维护者保存精确原版本和启动方式；不只保存版本号。
原域名、Nginx 配置、SSL 与现有守护设置保留受控副本，能恢复原入口；不更换域名、证书或其他站点配置。

备份放在 Web 根目录之外的受控位置，例如 /www/backup/yushuhub/，只允许授权维护者访问，并按既有制度保留异地副本。不要放到能通过域名下载的目录。

工具在停旧写入者后还会创建任务备份。它不能代替迁移前备份和恢复演练；回退也不会自动把旧数据库 dump 灌回去覆盖新记录。

预期：代理与维护者共同确认备份范围、位置及恢复负责人。备份里可能含密钥，不能作为普通故障截图发送。

4 · 领取发行单，安装独立控制器

维护者应给你一份完整发行单，不能只给一条“拉 latest”命令。发行单至少包含：

  • 当前受支持的基线 1.9.68、实例名、原目录、原端口和原 HTTPS 域名。
  • 可信来源的 delivery.py、控制器包、完整源码 SHA、二者 SHA256、生产更新公钥 keyId 与 SPKI 指纹。
  • 已批准的 HTTPS catalog 地址，以及 1.9.68 同版镜像项的 release ID。
  • 本地 mysqldump 路径、维护窗口、备份位置及资源预算。
本文未提供已发布的生产包或公钥。所有 REPLACE_…、example.invalid 和示例路径都必须由发行单替换。测试公钥、同一下载页自己给出的摘要都不能代替可信首次核对；不要关闭 HTTPS 证书校验。
维护者：校验与安装命令模板
BOOTSTRAP='/root/yushuhub-release/delivery.py'
ARCHIVE='/root/yushuhub-release/controller.tar.gz'
BOOTSTRAP_SHA='REPLACE_WITH_64_HEX'
ARCHIVE_SHA='REPLACE_WITH_64_HEX'
SOURCE_SHA='REPLACE_WITH_RELEASE_SOURCE_SHA'

printf '%s  %s\n' "$BOOTSTRAP_SHA" "$BOOTSTRAP" | sha256sum -c -
# 上一步必须显示 OK，之后才运行已核定的脚本
python3 -B "$BOOTSTRAP" verify --archive "$ARCHIVE" \
  --sha256 "$ARCHIVE_SHA" --revision "$SOURCE_SHA"
# 默认只读安装计划
python3 -B "$BOOTSTRAP" install --archive "$ARCHIVE" \
  --sha256 "$ARCHIVE_SHA" --revision "$SOURCE_SHA"
# 审阅后才应用；只安装/更新控制器，不迁移业务
python3 -B "$BOOTSTRAP" install --archive "$ARCHIVE" \
  --sha256 "$ARCHIVE_SHA" --revision "$SOURCE_SHA" --apply

预期：校验通过；只读计划无错误；应用返回 committed。如果依赖缺失、任务未收尾或注册不一致，停止处理，不绕过检查。

标准公有证书无需额外配置。业务中心若使用私有 CA，须在首迁前由维护者审核：纯证书包位于所有业务挂载之外、文件和父目录均 root 控制且不可被其他用户写入，路径/摘要纳入审批。不要把 TLS 私钥当 CA，更不要设 NODE_TLS_REJECT_UNAUTHORIZED=0。迁移后的环境或 CA 变更另需维护方案。

5 · 先完成 1.9.68 同版首迁

以下两轮计划有不同的审批摘要：登记 review SHA 与迁移 review SHA 不能混用。实例名和目录必须指向当前这一份后台。

维护者：先计划、再登记
INSTANCE='example-admin'
APP_ROOT='/www/wwwroot/example-admin'
PUBLIC_URL='https://admin.example.invalid'
CATALOG_URL='https://updates.example.invalid/pilot/catalog.json'
KEY_ID='REPLACE_WITH_APPROVED_KEY_ID'
KEY_SPKI='REPLACE_WITH_64_HEX'
INITIAL_RELEASE='REPLACE_WITH_APPROVED_1968_RELEASE_ID'
MYSQLDUMP='/www/server/mysql/bin/mysqldump'

/usr/local/sbin/yushuhub-upgrade-setup plan-registration \
  --instance "$INSTANCE" --app-root "$APP_ROOT" \
  --public-url "$PUBLIC_URL" \
  --catalog-url "$CATALOG_URL" --key-id "$KEY_ID" \
  --key-fingerprint "$KEY_SPKI" --initial-release "$INITIAL_RELEASE" \
  --mysqldump "$MYSQLDUMP"

核对 sourceVersion=1.9.68、原目录/端口/域名、授权模式、身份摘要、数据库定位摘要和初始 release；中心授权不应变为 legacy。维护者单独确认库归属，再填写本次返回的摘要：

REGISTER_REVIEW='REPLACE_WITH_REGISTRATION_REVIEW_SHA'
/usr/local/sbin/yushuhub-upgrade-setup register \
  --instance "$INSTANCE" --app-root "$APP_ROOT" \
  --public-url "$PUBLIC_URL" \
  --catalog-url "$CATALOG_URL" --key-id "$KEY_ID" \
  --key-fingerprint "$KEY_SPKI" --initial-release "$INITIAL_RELEASE" \
  --mysqldump "$MYSQLDUMP" --review-sha "$REGISTER_REVIEW" \
  --database-reviewed --apply

预期：registered。此时只登记，没有把业务切换到容器。

维护者：明确执行同版迁移
systemctl enable --now "yushuhub-upgrade@${INSTANCE}.service"
yushuhub-upgrade-setup plan-migration --instance "$INSTANCE"

# 审阅：sourceVersion 和 targetVersion 都必须是 1.9.68
MIGRATION_REVIEW='REPLACE_WITH_MIGRATION_REVIEW_SHA'
OP_ID='REPLACE_WITH_UNIQUE_OPERATION_ID'
yushuhub-upgrade-setup migrate --instance "$INSTANCE" \
  --review-sha "$MIGRATION_REVIEW" --operation-id "$OP_ID" --apply

yushuhub-upgrade info --instance "$INSTANCE"
yushuhub-upgrade status --instance "$INSTANCE"

预期：本次任务为 committed，实际 API 仍为 1.9.68；原端口由唯一业务容器提供服务，旧 PM2 不再占用。看到 accepted/running 不代表完成。

此时不要再从宝塔“Node 项目”启动旧 PM2，也不要使用 1.9.68 原网页的旧 ZIP 更新方式去修改容器。后续先由维护者走受验 CLI 升至支持控制器网页操作的批准版本。

代理检查：原地址登录、授权状态、旧用户/项目、余额、订单、会员和已有文件正常；由维护者在批准范围内做无付费功能核验。异常时保留任务编号，走恢复步骤，不重新填写整套经营配置。

6 · 保留原域名、SSL 和反代

本批使用 Linux host 网络，应用仅监听 127.0.0.1:原端口；沿用本机数据库的回环 TCP 连接。Compose 不需要 ports: 映射，宝塔容器列表的端口映射栏为空可能是正常现象。

如果原域名已通过宿主宝塔 Nginx 转发到这个地址，通常无需改域名、SSL 或目标端口。先验证原入口，不要为了让“Docker→网站”出现一条记录而再创建站点。

  1. 在左侧“网站”找到原域名，记录实际代理目标与证书。部分版本有独立“反向代理”项目，旧版在站点设置内。[4]
  2. 目标保留 http://127.0.0.1:原端口，发送域名/Host 应保留原域名；SSL 在现有入口终止，不把私钥放进业务容器。
  3. 需要调整时先备份该站点配置，只改此站点并检查 Nginx 配置，再平滑重载；不要停止或重装全机 Nginx。
  4. 验证 HTTPS 证书、/admin/v2/、/api/、静态资源、上传以及实际使用的长连接。
维护者：现有 Nginx location 配置参考（不是另建站点文件）
# 在原管理域名的有效 server 中核对唯一的 location /。
# 7077 只是示例，必须使用该实例原端口。
location / {
    proxy_pass http://127.0.0.1:7077;
    proxy_http_version 1.1;
    proxy_set_header Host $http_host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_connect_timeout 15s;
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
    proxy_buffering off;
    client_max_body_size 64m;
}

64m 和 300s 是需维护者核定的示例，不更改应用自身上传上限。JSON API 自身限制和 multipart 上传限制仍生效；有 CDN/WAF 时还要核对其超时/大小。不要在已有同名 location 外再粘一份，也不要缓存登录、API 和流式响应。[4][5]

# 路径仅为宝塔常见位置，先确认本机实际安装路径
/www/server/nginx/sbin/nginx -t
# 仅在检查通过且维护窗口允许时，使用该站点所用服务的平滑重载入口
若前置 Nginx 本身是 bridge 容器，此示例的回环目标不能直接套用。先由维护者确认网络和原入口方案；不要改业务为 bridge、不要暴露 MySQL，也不要在同机再抢占 80/443。

7 · 在宝塔看状态与日志

进入“Docker→容器”，按发行单中的实例名定位 yushuhub-<实例名>，刷新查看。可观察镜像、启动时间、healthy/starting、资源和日志；不要点击“升级/重建/删除”来更换业务版本。

INSTANCE='example-admin'
docker ps --filter "name=^/yushuhub-${INSTANCE}$" \
  --format '{{.Names}}  {{.Status}}  {{.Image}}'
systemctl is-active "yushuhub-upgrade@${INSTANCE}.service"
yushuhub-upgrade info --instance "$INSTANCE"
yushuhub-upgrade status --instance "$INSTANCE"
# 以下只在本机查看，分享前脱敏，不发送env/完整inspect/PM2 jlist
docker logs --tail 100 "yushuhub-${INSTANCE}"
journalctl -u "yushuhub-upgrade@${INSTANCE}.service" --no-pager -n 50

预期：控制器 active；业务最终 healthy；本次事务 committed。starting 期间等待控制器检查，不反复点重启。

默认日志采用 json-file、单文件 10MiB、保留 3 份；业务内文件日志、宝塔/Nginx 日志及数据库备份仍需原有保留策略，不代表整机日志总共只有 30MiB。

容器使用 unless-stopped。手工停止后它不会像故障退出那样自动恢复；不要把重启策略改成“停止后自动删除”，不要给此受管项目另设面板自动拉 latest 或重建计划。

文件权限由迁移工具按已审核范围处理。不要对 /www、数据库目录或业务根目录执行 chmod -R 777；权限异常交维护者核对数据路径和宿主 UID1000。

8 · 后续升级仍走受验入口

维护者先检查当前任务、备份和发行单，确认 catalog 明确支持当前版本。只允许固定 digest 的批准镜像，不能用面板“拉 latest”替代。

yushuhub-upgrade info --instance "$INSTANCE"
# 每次新动作使用维护者分配的新ID；重复读取同一动作保留原ID
OP_ID='REPLACE_WITH_UNIQUE_OPERATION_ID'
yushuhub-upgrade upgrade --instance "$INSTANCE" \
  --operation-id "$OP_ID" --apply

当实际运行版本已经支持新的升级页面，管理员可使用后台授权的升级/回退入口，它只提交给本实例的独立控制器。不能把这条新能力描述成原版 1.9.68 已自带。最终仍要核对任务 committed、实际 API 版本、原域名、授权及经营记录。

迁移后宿主原目录可能继续保留 1.9.68 代码作为恢复来源。此时不能用宿主 package.json 判断容器运行版本；以运行 API、实例任务和实际镜像为准。

宝塔负责观察和现有站点入口；业务版本变更由控制器负责。即便面板能编辑 Compose，也不要修改控制器生成的镜像、挂载、端口、用户、资源、套接字或审批状态文件。

9 · 失败时按任务恢复，不重装

  1. 停止连续点击，记录实例、operationId、stage 和错误代码。保留日志及备份。
  2. 先用终端查询 info/status。即使业务 HTTP 或网页不可用，独立 root CLI 仍可使用。
  3. rejected 通常表示切换前拒绝；处理原因后重新计划。rolled_back 表示已回退，核对实际版本与数据。
  4. needs_attention 或未知中断由维护者检查当前写入者、端口、镜像、配置与锁，再决定显式恢复，不能开第二个实例碰碰运气。
# 确认需要恢复未完成事务后，使用新的恢复ID
yushuhub-upgrade recover --instance "$INSTANCE" \
  --operation-id 'REPLACE_WITH_UNIQUE_RECOVERY_ID' --apply
# 只有维护者确认要撤回已完成业务升级时才执行
yushuhub-upgrade rollback --instance "$INSTANCE" \
  --operation-id 'REPLACE_WITH_UNIQUE_ROLLBACK_ID' --apply

业务回退沿原事务恢复上一受验版本，保留同一数据库和新增记录，不自动回灌旧数据库。控制器包安装中断是另一类问题：由维护者使用已验证的 bootstrap recover --apply；控制器包回退不是业务回退，也不是卸载已登记实例。

若只是误点宝塔“停止”，一个已经 committed 的事务执行 recover 不一定会替你启动容器。维护者先确认没有活动任务、旧 PM2 或其他写入者，且容器配置未变，再恢复原容器；不要创建新容器、重建卷或改 journal。

若面板已重建、改网络或删卷，先暂停操作并交维护者核实。不要把旧备份整库覆盖当前库当成默认修复，也不要删除任务收据或部署标记来骗过检查。

10 · 常见问题

现象先做什么
Docker→网站是空的看 Docker→容器及本机 docker ps，再看实例 info。网站记录不是容器全集，不重新创建后台。
容器编排找不到项目可能是面板版本或 JSON/外部项目识别差异。保留控制器归属，通过“容器”和 CLI 观察，不导入第二份编排。
容器端口栏为空当前是 host 网络，没有 ports 映射。核对回环监听与原反代，不额外映射公网端口。
首迁后还是 1.9.68正常：首次必须同版本。已批准的后续版本要另提交升级任务。
网页版本和本机不同分别核对本机实际 API、原域名 API、容器及任务。再检查反代目标/CDN缓存/浏览器缓存，不把“环境不同”直接当根因。
502 或长连接中断先看原目标端口有没有服务、本机 API，再核对代理网络、Host/转发协议、WebSocket/超时和缓存。不要重装 Nginx。
数据库连不上核对仍是 host 网络、本机 TCP 地址/端口及原服务状态。不要改成 host.docker.internal、改所有人可连或开放公网。
权限不足/上传失败查看准确的数据挂载及 UID1000 权限；不把应用源码变成可写，不全盘 chmod。
PLAN_CHANGED / 配置变化先停止，重新审阅当前计划。迁移后 env/CA 变更需单独维护方案，不修改摘要/current 文件绕过。
授权显示 disabled/expired检查原授权及受信中心连通，交授权维护者处理；不能把容器绿色等同业务许可有效，不能切 legacy 绕过。
镜像下载失败让维护者核对发行单 digest、仓库可达与证书。不要改成同名 latest、关闭TLS或随意更换镜像站。

11 · 新部署的支持现状

当前工具的登记入口要求已经健康运行的单实例 PM2 管理后台。它不会初始化空库、创建数据库账号、生成首次业务身份、配置新授权或一键安装 Nginx/Docker。

所以，一台仅装了宝塔的新机器，不能靠导入本文 Compose 或点击应用商店获得等价的受管新部署。本项目当前尚未发布宝塔 YushuHub 一键模板。

已有完整 1.9.68 实例可以按前述迁移流程。纯新部署若要扩展，需另行批准最小范围：本地空库及最小权限账号、首次数据/密钥初始化、合法授权接入、固定镜像/挂载与实例登记、原生恢复入口、域名SSL及备份验收。本手册不让代理自行绕过 PM2 首迁校验。
