# 版本发布与更新源

YushuHub 是管理端唯一主研发仓库，日常修改只提交这里。旧私有仓库保留历史，不继续双写；桌面端独立维护。

## 源码与运行版本

首次公开源码接续管理端 1.9.56，不重新占用旧版本标签，不因文档和仓库迁移改写现网版本。master 包含最新合并内容，生产版本以经验证的版本标签、package.json 和正式更新清单为准。

GitHub 提交、GitHub Release 与生产部署是不同动作。公开源码不会自动更新用户的服务。现有官方自更新源保持兼容，不把 GitHub 分支地址当作更新清单。

## 完整发版的完成条件

维护者明确要求“管理端合并主分支并发版”等完整发版操作时，应连续完成内部管理端发版手册中的生产部署、官方交付源发布和下游验收。该指令包含本次管理端生产部署及官方更新源发布授权；不能只完成 GitHub Release 就报告发版完成。仅要求提交、合并或发布源码时，按明确范围执行。

完整发版必须同时确认：主分支和不可变标签已推送、官方生产运行新版本、唯一官方清单与 ZIP 已发布、公网下载摘要一致、下游能够发现更新并通过下载及包内版本校验、发布记录已保存并提交。下游实际升级仍需单独明确授权。内部运维手册保存在受控私有位置，本公开文档不替代其部署、备份、回滚与验收步骤。

## 维护者发布步骤

1. 从最新 master 创建分支，完成修改及领域回归。执行 npm run check、npm run test:distribution、node scripts/smoke-test-frontend.mjs 和 node scripts/smoke-test-imports.mjs；前端变更追加类型、测试、架构检查和生产构建。
2. 更新 package.json 与锁文件版本，在 docs/UPDATE_HISTORY.json 追加用户可读说明；核对构建产物，检查凭据和内部资料。
3. 合并到 master，创建不覆盖旧标签的正式版本标签；发布说明写明改动、升级要求和验证边界。
4. 需要授权交付 ZIP 时运行 npm run pack:zip -- -Version <版本>，审核 ZIP 隔离检查、版本和 SHA-256；打包本身不部署。
5. 生产部署和官方更新源发布需明确授权；已获完整管理端发版授权时，继续按内部发版手册执行，无需重复请求同一授权。内部服务器身份、上传凭据及操作记录放在独立私有运维位置；不得加入公开仓库。
6. 验证健康、关键 API、静态资源、更新发现与下载摘要；保留回滚包和数据库备份。自建站点应配置自己的更新源并自行验证。

初次公开不替代正式交付包，也不宣称中心构建服务或付费供应商接口已经完成公开联调。
