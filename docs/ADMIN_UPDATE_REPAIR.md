# 管理端升级验证与部署修复

管理端 1.9.69 和独立部署工具 1.3.0 提供以下能力。服务器一键安装入口固定下载工具 1.3.0，并校验对应 SHA-256；已打开的旧工具需要关闭后重新执行安装命令。

## 升级如何判定成功

系统内更新和独立工具使用相同的端口归属规则：监听进程可以是选中的 PM2 进程，也可以是它在同一应用目录下的子孙进程。通过 npm 启动时不再仅因父子 PID 不同而失败。所有可见的监听者均须归属该实例；检查失败、PID 不可见、端口冲突或多个在线候选实例，都不能直接报告升级成功。

重启后要求同一新 PID 连续三轮通过端口、运行版本、本地管理页面及 JS/CSS 类型检查；配置公网地址时还要检查公网前端。PM2 表格中的应用版本字段和 `online` 本身都不是成功依据。

系统内更新会在替换文件前验证进程归属。下载包经过摘要、归属、路径及符号链接检查；替换文件或安装依赖阶段失败时恢复操作前代码，并记录恢复结果。重启后的验证失败保留失败状态、实际监听 PID、父 PID、应用目录、PM2 记录和备份，供后续修复；此阶段不会擅自终止其他监听者。

## 独立工具中的修复

在“升级与维护”填写现有实例的应用目录和公网 URL，先选择“运行诊断”或“预览修复方案”。端口读取自目标 `.env`，实例优先复用相同目录下的实际 PM2 名称，包括历史名称。诊断不会因存在多个候选实例而直接停止采集。

默认修复执行以下操作：

1. 备份本次操作前的程序文件。
2. 重新安装当前版本的生产依赖，有锁文件时使用 `npm ci`；不执行安装生命周期脚本。
3. 使用目标配置中的端口和实际实例名称重启现有 PM2 记录；记录缺失时，以现有应用入口和 `.env` 重建。
4. 验证端口、运行版本及本地和公网前端。

勾选“同时使用上方 ZIP 恢复程序文件”可以修复丢失或损坏的应用文件。ZIP 必须与目标 `package.json` 中的当前版本一致；修复不会把“最新版”静默当作同版本包。需要改变版本时使用“开始升级”。当前版本无法从 `package.json` 确定，或缺失 `.env` 时，工具会停止，要求先恢复已知配置或版本身份。

预览显示目录、端口、PM2 名称、当前版本和具体步骤。执行时重新核对实例 PID、配置、关键文件及程序包摘要；任一变化都要求重新预览。修改表单或切换程序包来源也会使页面上的预览失效。

工具不覆盖 `.env`、授权连接、上传资源、更新产物及运行数据，不重置数据库和管理员。启动应用仍会执行该版本正常的启动逻辑；代码快照不是数据库备份，跨版本升级前仍应保留数据库备份。

## 失败恢复与并发

独立工具的升级、修复和回滚都保存操作前的代码快照，失败时恢复这个准确快照，而不是从历史发布目录猜一个版本。原实例在线时还要验证恢复后的版本；原实例停止或缺失时恢复其原有状态。恢复未通过会明确报告 `rollback-failed`，不会把一次 PM2 `online` 输出当作恢复完成。

最近三份代码快照位于 `data/deployer-backups/`；操作记录位于 `data/deployer-receipts/`，包括原版本、目标版本、备份目录、失败原因和恢复结果。“回滚版本”优先使用这些快照，并兼容原 `releases/` 目录；留空选择最近一个不同版本的可用快照。

两条更新入口使用相同的 `data/self-update/maintenance.lock/` 防止并行覆盖。系统内更新的锁由独立验证进程在结束时释放。若服务器或执行进程被强制终止，锁会保留；先核对 `owner.json` 及实际进程后人工处理，工具不会仅凭锁的时间自动抢占。

## 无 SSH 时的排查材料

代理商可以在自己的宝塔终端启动新工具，使用“运行诊断”或“预览修复方案”，并回传页面日志；无需向维护方提供 SSH 密码。新版后台的诊断导出还包含 `restartStatus`、`restartLogTail` 和 `runtimeDiagnostics`。PM2 诊断只输出选定的进程字段，不导出完整环境变量。

常见错误会区分为：

| 错误 | 含义 |
| --- | --- |
| `PORT_OWNERSHIP_CONFLICT` | 监听者不是选中的 PM2 实例及其应用子孙进程 |
| `PORT_OWNER_UNAVAILABLE` | 已有监听，但当前权限看不到 PID |
| `PORT_INSPECTION_FAILED` | `ss` 不可用或执行失败 |
| `PORT_NOT_LISTENING` | 目标端口尚未监听 |
| `PM2_DIRECTORY_MISMATCH` | PM2 指向其他应用目录 |
| `PM2_AMBIGUOUS` | 名称或在线实例不唯一 |
| `PM2_PID_UNCHANGED` | 重启后尚未切换为新进程 |

真实监听冲突、多个候选实例和权限不明的场景，需要依据诊断证据处理。修复功能不会批量杀进程、删除其他 PM2 应用或关闭校验。

## 开发验证

执行 `npm run check` 和 `npm test --prefix tools/admin-deployer`。专项测试覆盖父子 PID、真实冲突、不可见 PID、依赖失败、同版本补包、准确回退、预览失效和并发锁。

2026-11-09 在原生 Linux 测试服务器完成 16 项验收，使用 Node.js 24、PM2 7、独立 MySQL 5.7 和 Nginx 反向代理。以官方 1.9.62 ZIP 首次安装后，实际执行后台更新、工具升级、手动回滚、同版本补文件、PM2 记录重建、旧端口环境修复、npm 包装进程更新，以及依赖失败和启动崩溃后的自动回退；并验证重复实例、其他进程占用端口和并发维护的拦截。测试用户、积分余额、积分流水、管理员认证信息、配置和保留文件的校验值保持一致。验收使用独立候选包；这些结果不等同于确认某个下游部署的现场根因。

`tools/admin-deployer/test/runtime-linux.integration.mjs` 使用真实 Linux PM2 和 `ss` 验证直接 Node 启动、npm 包装启动、实际重启和跨实例端口冲突。运行时将仓库只读挂载到隔离容器的 `/source`，不连接业务数据库或真实供应商。

浏览器专项 `tools/admin-deployer/test/gui-browser.integration.mjs` 使用独立无头 Chrome 配置目录和模拟维护请求，验证没有预览时不执行修复、方案传递及修改配置后失效；需设置 `ADMIN_TEST_CHROME`，并在本机 47831 端口启动带测试令牌的工具页面。
