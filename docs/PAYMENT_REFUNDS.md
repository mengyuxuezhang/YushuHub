# 支付订单退款实现与验收

本模块处理终端支付订单售后，与模型调用退积分分开。测试开关下已实现预览、全额原路申请、权益暂扣、持久恢复、受控人工核对及后台页面；真实商户联调等门槛尚未通过，不能视为生产现金退款已完成。

## 业务与权限

- 首版每个原订单只登记一笔固定编号的全额原路退款，不支持部分退款、代理提现或自动分账，也不增加代理供货余额。已关闭的退款不通过换指令重新创建；关闭后重试流程仍待实现。
- 所属组织的启用所有者并具备payments.manage才可处理。一级默认不能处理二级终端，员工不能发起；组织、实际金额、原交易、审计人来自服务端会话和订单，不采用请求体覆盖。
- 中心授权暂停/到期仍可处理原现金售后，新充值、购买、支付配置修改继续拒绝。现金操作使用本组织原收款配置，不使用官方模型或构建服务凭据。
- 新订单发放前保存原有效会员及实际发放凭证；旧单缺证明、原会员被覆盖/到期、原发放积分不足或已到期、尚有未结模型/音色/供货预占时拒绝自动受理，不猜算历史权益。

## 持久状态与原子权益

既有数据库初始化入口创建ai_payment_fulfillments、ai_payment_refunds和ai_payment_refund_events，业务请求不执行DDL。

1. 支付成功发放在原订单/用户事务内记录发放前会员、实际新会员、原积分流水和六位小数积分、支付身份及金额；JSON稳定摘要不受数据库键重排影响。重复支付回调不重发，也不为旧已支付订单补造发放前状态。
2. 新订单从服务端配置冻结非秘密商户身份（微信AppID/商户号，支付宝AppID/收款账号/正式或沙箱环境）；终端响应剔除内部字段，凭证不含私钥或密钥摘要。正常密钥轮换不改变身份，换账号或环境须停止并核对，不能取当前账号冒充旧账号。
3. 预览只读取，展示退款额、撤回积分、当前及暂扣后余额、被冻结和拟恢复的会员。受理时短事务锁定原订单和用户，重新校验摘要和原权益；同一指令幂等，不同内容不能覆盖原退款。
4. 先暂扣本次原发放积分、冻结购买会员，提供本组织不发赠送积分的免费权益，保存固定退款编号与审计事件，再释放事务访问支付平台。会员发放、手工取消、购买与免费回退识别处理中状态；普通原支付查询/关闭不接管退款。
5. 发送前保存submitted阶段，120秒租约串行处理；已提交或发送结果未知只查原编号，不重新发送。每分钟调度、每批最多20条、失败持久退避最长一小时。平台处理中、查无记录、异常、缺状态均保持暂扣。
6. 明确平台结果先单独持久化，再处理本地权益。最终本地事务失败时可从原凭证恢复，不需再次退款或查询；商户后续修改不影响已确认现金结果的本地完成。未知结果不能利用换号查询放行。
7. 成功后将原订单置为refunded、按原日期恢复仍适用的前期会员，或保留免费权益；明确关闭时恢复仍有效的原购买会员，只将未过原有效期的暂扣积分加回当时余额。已过期的暂扣积分不重复扣除、不重新发放，以held_points_expired事件记录原数量和原期限；购买会员已到期但积分仍有效时，免费权益保留原积分期限，不覆盖期间其他消费或延长原期限。原发放/消费流水及上游余额不改，以关联退款编号的暂扣/返还积分流水和不可变事件表达变化。
8. 项目删除不得再擦除有关联订单或积分流水的终端用户；购买建单也锁定用户，避免与删除并发。可停用项目/用户继续保留账务资料。

## 接口与开关

管理员接口均要求payments.manage；除状态元信息外，还要求本组织的启用所有者：

| 接口 | 用途 |
| --- | --- |
| GET /api/payment-refunds/state | 新受理开关及历史处理可用性 |
| POST /api/payment-orders/:id/refund-preview | 原权益及金额预览 |
| POST /api/payment-orders/:id/refund | 原预览摘要、commandId、reason、confirmEntitlements=true受理 |
| GET /api/payment-orders/:id/refund | 本组织原退款状态 |
| POST /api/payment-orders/:id/refund-query | 按原编号受限恢复，遵循持久退避 |
| POST /api/payment-orders/:id/refund-resolve | 原编号、resolutionId、最终结果、providerFinal=true及凭证的受控核对 |
| GET /api/payment-orders/:id/refund-events | 本组织原退款审计记录 |

AI_PAYMENT_REFUNDS_ENABLED默认0，只控制新预览/受理。关闭新受理后，历史读取、查询及已受理任务调度仍保留；关开关不是撤销已批准退款。界面仅在原订单存在售后记录或明确启用新受理时向所有者显示入口。回复丢失保留原指令和预览，不另行打款；服务端明确拒绝过期预览后可重新预览。

## 未知结果的受控核对

仅允许无活动租约、无已确认平台结果的unknown，或明确未发送的prepared。已发送的原退款必须匹配原商户，先释放数据库事务再查询原平台：平台返回成功/关闭时以平台结果为准，仍在处理则拒绝人工完结并保留暂扣。查询失败或仍未知时，所有者须凭原商户最终账单/工单声明最终结果；文字凭证是经营方审核责任，不是机器验证银行到账的证据。明确未发送的申请只能取消。

原resolutionId、实际操作者、结论、凭证和查询观测持久保存；回复丢失只按完全相同的指令恢复，不再发送现金。确认结果先落库再处理权益，本地失败由工作器继续完成；不能覆盖已有明确结果。界面提供原编号、凭证及审计时间线，关闭新受理后仍可核对历史。

## 供应商协议

复用原微信/支付宝RSA签名传输，拒绝重定向、HTTP错误、验签错误和不同交易/订单/编号/币种/金额；金额是安全整数分，不以浮点计账。返回和持久化只保留受限结果，不存原始支付人数据或签名秘密。

微信固定out_refund_no：SUCCESS成功、PROCESSING处理中、CLOSED明确关闭，ABNORMAL及查无记录保留未知。支付宝固定out_request_no：申请fund_change=Y且原交易/金额核验通过才成功；N或无状态不代表失败，查询须REFUND_SUCCESS及原交易/编号/金额全部匹配。适配器不自动重发现金。

依据（2026-10-31核对）：[微信申请](https://pay.wechatpay.cn/doc/v3/merchant/4012791883)、[微信查询](https://pay.wechatpay.cn/doc/v3/merchant/4012791884)、[支付宝退款](https://aipay.alipay.com/docs/subscribe/api-list/other-basic-interfaces/alipay-trade-refund.html)、[支付宝查询](https://aipay.alipay.com/docs/vibe-pay/ai-web-app-payment-qianyi/api-list/alipay-trade-fastpay-refund-query.html)。

## 迁入与回退

源库有以上表时纳入orders核对摘要；旧库缺表仍可采集。待处理现金退款列为绑定切换阻断项。只要已有现金退款记录，就要求兼容新退款账务的版本回退，不能恢复旧数据库快照覆盖暂扣、现金确认或事件。

## 已有验证与剩余门槛

后台205、前端155、类型/175源文件架构/生产构建及原支付/会员烟测通过。MySQL8.4和测试服务器5.7各21项领域场景中包含现金退款真实SQL/HTTP模拟：原归属/到期权限、10路并发、暂扣一次、免费权益不发积分、未结旧模型/音色/供货阻断、商户变化、提交成功回复丢失、平台成功但本地提交失败、租约恢复时旧发送仍在进行、原结果只确认一次、当前余额返还、历史缺证明拒绝。另有签名HTTP协议模拟、两端原资源分发HTTP及本地原账务备份恢复/并发基线。测试未发起真实退款或新增供应商付费；这些不等于现金数据专项灾备或真实商户验收。

仍需：关闭后重新申请策略、旧单凭证受控重建、生产现金告警/备份配置及正式商户沙箱或小额授权联调。完成这些门槛前不启用生产新受理，不改正式更新源。

现金只读巡检、去重告警及虚构库mysqldump恢复说明见[监控与恢复](ACCOUNTING_MONITORING.md#现金退款巡检2026-10-31)。每轮最多100笔，完整干净扫描才解除核对异常；恢复原未知结果仅查询原退款编号。原平台实时资金对账仍需真实商户验收，不以本地巡检代替银行凭证。
