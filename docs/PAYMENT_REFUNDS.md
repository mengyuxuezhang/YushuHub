# 支付订单退款实现与验收

适用主规划中的终端支付售后，区别于已结算模型调用的退积分。当前只完成供应商协议适配，尚未开放退款入口，也不代表现金退款闭环已完成。

## 业务与权限

- 首版只支持原订单单笔全额原路退回，不支持部分退款、代理提现、自动分账或将退款转入上游钱包。
- 所属组织所有者且有支付权限才能发起，员工及一级默认不能处理二级终端订单。归属、原金额和原交易从服务端订单解析，不信任请求体。
- 到期/暂停保留售后处理，新充值和购买仍拒绝；关闭或撤销的官方服务凭据不能用于现金操作。
- 先预览影响，再提交明确的退款原因和幂等编号。预览须说明原支付金额、将撤回的积分/会员及恢复的前期会员期限。原优惠已消费不补扣上游费用，不把现金充值或退款算成模型利润。

## 待实现的本地事务与恢复

1. 新订单发放权益时，在原事务中保存不可变发放凭证：旧有效会员记录、实际发放积分、订单/用户/组织、原会员和新会员身份。不得从当前套餐推算历史权益。
2. 退款只处理可证明的原权益。若会员已被后续购买/手工变更覆盖、积分不足、存在未结供货请求或缺少发放凭证，自动流程拒绝，列为需核对；不能覆盖新会员或静默制造积分欠款。
3. 事务锁定原订单与用户，扣住本次撤回积分、冻结原购买会员、持久化唯一退款编号和事件后，才允许访问支付平台。不得持有数据库事务等待网络。
4. 同一用户的会员发放/取消/免费回退及支付发放需识别退款处理中状态，避免回退或新权益与退款互相覆盖。扣住的积分不能继续消费；其他不相关账务流水不可修改。
5. 响应丢失、进程重启或平台处理中时保留原编号、原金额、原商户绑定及权益冻结状态，先查询原退款，不能换编号重发。明确成功才在同一事务内记录已退款、完成权益撤回并恢复仍适用的原会员；明确关闭才恢复本次冻结权益。查无记录、异常或未知不能自动解冻。
6. 原始支付/积分流水保留，用关联原订单的退款事件及冲正记录表达变更。退款不增加代理供货余额。并发请求、重复通知、重启及丢失提交响应必须只完成一次。
7. 历史订单没有完整发放前状态时，不自动编造恢复凭证。需受控核对工具明确影响与凭证后再处理；在此之前返回明确拒绝，不调用支付平台。

## 已有供应商适配（2026-10-31）

`payment-refund-providers.mjs`共享现有微信和支付宝签名传输。所有金额以整数分校验，仅支持原交易全额，退款编号和原交易必填。输出只含受限状态及退款标识，不保存支付人信息或商户秘密。

微信使用固定out_refund_no申请和查询，验证签名后核对原订单、平台交易、退款编号、币种、原金额和退款额；SUCCESS成功、PROCESSING处理中、CLOSED明确关闭，ABNORMAL/未知/查无记录保留未知。支付宝始终传out_request_no，申请fund_change=Y且原交易/金额匹配才成功；N或状态缺失不代表失败，查询仅REFUND_SUCCESS及原交易/编号/金额全部匹配才成功。HTTP错误或验签失败不能记成功。适配器不自动重试现金转移。

五项模拟签名HTTP测试覆盖申请/查询、整数分、篡改、不同订单或金额、缺状态、处理中、异常、查无记录和拒绝部分退款。未向真实支付平台发起退款。仍需上述本地事务、售后UI、后台恢复、数据库并发/崩溃测试及完整隔离验收。
