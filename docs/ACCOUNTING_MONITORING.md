# 供货监控、Webhook与到期任务恢复

本页记录开发分支已实现能力。它不代表生产部署或7天试点完成；总进度见[接手清单](AUTHORIZATION_SUPPLY_STATUS.md)。

## 启用及升级

官方网关与一级管理端分别采集自己的账本，默认每60秒采集及投递。官方账本为`official-v2`，本地为`commerce-v2`。监控配置、异常状态和发送队列放在独立`licensing_state`记录`<book>-monitor`，不与钱包锁共用事务，不参与模型扣款。

升级前备份并停止相应服务，按[账务切换说明](ACCOUNTING_STORAGE.md)显式执行原有初始化/迁移命令。已有账本重复执行仅补建缺少的监控记录，保留钱包、流水、预占和配置。启动不执行DDL；没有监控记录时拒绝启动，不能靠删除账本或重新导入解决。

设置受控密钥文件：

- 官方：`AI_GATEWAY_MONITOR_KEY_FILE`，默认`data/gateway-monitor.key`。
- 一级：`AI_ACCOUNTING_MONITOR_KEY_FILE`，默认`data/accounting-monitor.key`。

密钥首次保存配置时生成，AES-256-GCM加密Webhook地址与可选机器人签名密钥，绑定账本身份。密钥文件须和数据库分别备份并受访问控制；只恢复数据库无法解密地址。不要把密钥文件、真实Webhook、运营账号或服务配置提交Git。

## 配置与查询接口

| 场景 | 基础路径 | 权限 |
| --- | --- | --- |
| 官方网关 | `/api/model-gateway/v1/operator/monitor` | 网关运营账号登录并通过MFA后的Bearer会话 |
| 一级管理端 | `/api/authorization/monitor` | 已登录的一级组织所有者；员工及二级均拒绝 |

接口如下，均沿用`{success,data}`响应：

- `GET <基础路径>`：脱敏配置、采集时间/指标、异常状态、最近100条发送记录和最近50条配置操作。完整地址、密文、签名密钥均不返回。
- `PUT <基础路径>/config`：`{expectedVersion,enabled,url?,signingSecret?,thresholds?}`。首次启用提供飞书机器人HTTPS地址；之后省略地址保留原值，提供新地址立即生效。修改签名密钥须同时提供地址，留空表示移除签名密钥。版本冲突返回409，先重新读取版本，禁止覆盖他人更新。
- `POST <基础路径>/test`：`{requestId}`。相同请求编号不会重复排队；测试文字明确标注验收测试、不涉及真实资金或用户。后台工作器随后发送。

只支持飞书`open.feishu.cn/open-apis/bot/v2/hook/...`地址；以后需要其他Webhook协议时新增适配器。按[飞书自定义机器人协议](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)发送文本和可选签名；HTTP成功且业务`code=0`（兼容旧`StatusCode=0`）才算送达，非零业务码进入重试。机器人若配置关键词/IP限制，需确保服务器与消息内容匹配。

地址更新后，未发送及重试消息使用新地址；已经发出的请求无法撤回。`enabled=false`暂停投递但保留队列与采集。一级授权到期后所有者仍可查看/调整监控；这不恢复任何经营权限。一级授权页已提供本级资金告警配置界面（启用的一级所有者可见）；独立Prometheus采集令牌尚未提供。

## 指标与告警

采集未知结果数量、未释放预占的最长存续时间、未确认结算事件数量/最长等待、欠款钱包数；官方额外统计本进程本轮鉴权拒绝/不可用次数，本地检查授权同步状态及最近成功校验时间。恢复工作器错误也计入本进程本轮指标。计数用于运维，不能作为财务报表或跨进程精确累计。

每轮在一致数据库快照下巡检最多100个钱包，将余额与不可变流水汇总对比、预占与有效持有汇总对比。轮转扫描全钱包后记录完成时间；异常须后续完整扫描无异常才恢复，不能以一个干净分页清除异常。此处巡检不覆盖终端积分账全量守恒，仍需迁移/周期对账工具。

默认阈值，可通过`thresholds`调整：

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| staleHoldMs | 300000 | 预占从请求受理起计龄，轮询刷新更新时间不会隐藏滞留 |
| eventAgeMs | 120000 | 结算事件最长等待 |
| eventCount | 100 | 未确认结算事件数 |
| rejectionCount | 10 | 本进程本轮官方鉴权失败次数 |
| syncAgeMs | 120000 | 已激活一级授权最近成功同步距今时间 |

未知结果、欠款、资金不守恒、恢复错误达到1条即触发；授权明确拒绝也触发。长异步模型可能正常持有预占较久，应按业务上限设置阈值。

只在异常首次出现和恢复时生成事件，不按每分钟重复推送；消息只包含固定账本名称、聚合数量和稳定事件ID，不含用户、提示词、结果或密钥。配置及测试操作留最近100条运维审计，资金审计仍以不可变财务流水为准。

每次最多投递5条，10秒网络超时，30秒持久租约，失败指数退避最大5分钟；进程重启后租约到期可接手。保存全部待发消息（最多200）及最近100条成功历史；队列满会保留原消息并暴露`lastScanError=ALERT_QUEUE_FULL`，需修复地址并清空积压。禁止记录原始网络错误，避免Webhook路径泄漏。

通知采用至少一次投递：飞书已接收而本机未记录成功时，重试可能出现相同事件ID的消息。资金/请求结算幂等不依赖通知是否送达。配置读取接口显示发送失败及采集失败；进程/数据库完全停机、所有发送出口中断仍需外部存活监控，不能依赖自身Webhook发现自身断电。

## 授权到期后的已受理任务

中心新增`POST /api/license-center/v1/recovery-token`，使用当前绑定实例凭据，提交`{organizationId,requestId}`。签发有效期60秒、用途`official-model-recovery`的凭据，限定`status,poll,ack`三个动作及单一请求编号。它不经过普通授权宽限缓存，不改变本地拒绝标记或签发普通调用权限。

网关新增：

- `GET /api/model-gateway/v1/recovery/requests/:id`
- `POST /api/model-gateway/v1/recovery/requests/:id/poll`
- `POST /api/model-gateway/v1/recovery/requests/:id/ack`

网关再次在线核对中心签名、版本、实例、层级与父子关系，并检查请求已存在、钱包属于该一级、快照组织与凭据组织一致。缺失请求不能创建；不能用于目录、新推理、充值、改价、构建或其他请求。

一级或二级到期/暂停仍能处理原请求；原异步任务只查询原供应商任务，不重新提交，按原价格快照结算。模型已下架也可查询原任务，但若原版本/查询适配器配置不再存在，转人工核对，不切换到新模型。换机后旧凭据立即失效；新实例凭据可恢复同组织原请求。授权撤销则禁止自动恢复，需官方运营携供应商证据人工对账。自接模型未知结果仍禁止盲目重发。

本地30秒工作器使用该专用凭据，不要求重新取得有效经营授权；先完成本地积分/供货结算事务，再确认官方事件。授权失效后的退款、导出细粒度权限仍另列待办。

## 组织调价通知与界面（2026-10-30）

授权页新增“本组织调价通知”，一、二级启用的所有者分别管理自己的地址。基础路径 `/api/supply/notifications`，同样提供GET状态、PUT `/config`、POST `/test`，字段及乐观版本规则与资金告警一致。服务端从可信组织会话解析授权ID，请求中的组织ID不能切换目标；员工、停用成员不能配置。失效后仍允许所有者查看、更换通知地址，不恢复经营权限。一级资金告警与本组织调价通知是不同配置，二级不接触一级资金通道。

备份后按迁移工具要求显式设置 `AI_AUTHORIZATION_LOCAL_MIGRATION=approved` 与目标库环境变量，再运行 `node scripts/authorization-local-migrate.mjs` 后，本地 `licensing_state` 新增 `commerce-v2-price-notifications` 记录；禁止运行时自动建表。各组织的地址分别加密并绑定组织身份。密钥文件为 `AI_PRICE_NOTIFICATIONS_KEY_FILE`（默认 `data/price-notifications.key`），须与数据库分别受控备份。缺少密钥时投递保留为待重试并显示 `WEBHOOK_UNAVAILABLE`；恢复原密钥后继续，不可生成替代密钥冒充恢复。

每60秒读取已激活且有效的授权及按组织计算的未来价表，为官方底价、一级供货、二级加价、积分比例及倍率变化生成稳定事件ID。消息提供组织、模型、生效时间和查看路径，不携带供应商成本、用户内容或完整接收地址。队列重启可恢复；去重键单独保存至价格生效，避免成功历史分页裁剪造成重复入队。每组织最多100条待发调价通知；超额计入 `noticeBacklog` 并由下一轮价表扫描补排。每轮轮转最多5个组织、每组织最多2次投递，和资金告警的采集/发送分别运行。过了生效时间尚未发出的调价通知标记跳过，不发送误导性的“未来调价”；这类失败须运营核查，不能视为已按时送达。

界面仅显示目标主机、配置版本及最近投递状态，不回显完整地址或密钥；更新地址不清空原告警阈值。通知仍为至少一次，响应丢失可能重复，正式接收通道和运营响应必须在试点确认。尚无通道的组织保留通知，但不能据此宣称所有代理已收到。API/界面提前价表与外部投递是两类证据。

本轮：后台179项、前端142项、类型/架构检查、管理端与中心构建通过。MySQL 8.4.10与测试服务器5.7.44八项集成覆盖组织隔离、换址、重启去重、租约、失败重试、密钥丢失后恢复；8.4另完成财务备份恢复和1000请求数据库基线。测试服务器新建库实际启动管理服务，一二级配置各自通知、伪造组织ID、中心暂停后重启读取均通过；一级资金通道未被修改。本轮通知使用模拟发送或停用的虚构地址，未向真实收件人发送、未调用付费模型、未改现有经营库。

## 现金退款巡检（2026-10-31）

中心接入的一级管理端沿用原一级资金告警通道，配置入口和加密地址不变，无需额外提供Webhook。每轮同时只读采集现金待处理、结果未知和最早受理年龄；unknown立即告警，待处理超过原staleHoldMs阈值告警。只发送汇总数量，不包含用户、订单编号、银行凭证、商户配置或支付内容。状态不变不重复排队，异常消除后发送恢复；重启和并发投递沿用原持久状态及租约。仍不代替外部停机监控。

现金对账每轮在一致性读取事务中扫描最多100笔，按原订单游标持续巡检：核验原发放凭证摘要、原商户身份、退款指令摘要、全额金额、原暂扣/返还流水、过期暂扣与返还数量守恒、订单状态以及确认/结束审计事件。不会查询支付平台、修复数据或用当前用户总余额推算历史退款。一轮干净的分页不能清除上一轮异常；须完整扫描无差异才解除。大库发现时延受每分钟100笔上限影响，应通过实际容量试点再核定。缺少整套旧表按未接入处理，部分缺表则扫描失败，不宣称正常。

现金数据备份恢复验收由npm run test:licensing:mysql中的原订单测试执行：在本次新建MySQL8.4容器内用mysqldump备份整个虚构经营测试库，恢复到独立新库，比对所有表摘要，再恢复原未知退款。恢复只查询同一个退款编号，重复恢复不再打款、暂扣不再扣第二次，源库保持不变，测试结束仅清理本次新建库。该验收不涵盖真实商户密钥丢失、生产备份保留/加密或跨版本容灾；正式部署仍须分别备份数据库与原加密密钥。
